# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MyBatis Repository is a Java 8 library published to Maven Central (`io.github.bestheroz:mybatis-repository`). It gives MyBatis mappers generic CRUD methods — no SQL, no XML — by generating statements at runtime from JPA annotations on the entity.

All production code lives in `src/main/java/io/github/bestheroz/mybatis/` — 12 files, ~2,290 lines. There is no sample app and no database in this repo.

## Build and Test

```bash
./gradlew test                      # runs tests; finalizedBy jacocoTestReport, so the report is always produced
./gradlew test --tests "io.github.bestheroz.mybatis.MybatisStringHelperTest"
./gradlew test --tests "io.github.bestheroz.mybatis.MybatisStringHelperTest.escapeSingleQuote_ShouldEscapeCorrectly"
./gradlew spotlessApply             # required before committing
./gradlew spotlessCheck
./gradlew check jar                 # what CI runs — use this, not `build`
./gradlew dependencyUpdates         # ben-manes versions report
```

**Do not use `./gradlew build`.** The `org.springframework.boot` plugin is applied to what is actually a library, so `bootJar` fails with `Main class name has not been configured and it could not be resolved`. This is long-standing and unrelated to any change you make; CI sidesteps it by running `check jar`.

### Toolchain constraints (important)

The build sits in a narrow JDK window — **JDK 17 is the tested one** (`.github/workflows/*.yml`):

- **JDK 8 cannot compile this project.** `jakarta.annotation-api:3.0.0` is Java 11 bytecode (major 55) and `MybatisAutoConfiguration` references `@jakarta.annotation.PostConstruct` directly, so javac 8 fails with `class file has wrong version 55.0, should be 52.0`. Building on 8 is not an option, regardless of the Java 8 *target*.
- **JDK 11 cannot configure this project.** `com.vanniktech.maven.publish:0.37.0` requires JVM 17+; the build fails at configuration time with `Dependency requires at least JVM runtime version 17`.
- **Gradle must stay on 8.x.** The `org.springframework.boot` 2.7.18 plugin uses Gradle APIs removed in Gradle 9; with a 9.x wrapper even `compileJava` fails at `Failed to notify dependency resolution listener > LenientConfiguration.getFiles()`. 8.14.3 is known-good.
- **Google Java Format is capped by the build JVM**, and Spotless reports the mismatch as a confusing `Cannot fingerprint input property 'stepsInternalEquality' ... cannot be serialized` failure rather than a plain message. 1.28.0 needs JVM 17+, 1.30.0 needs JVM 21+, so the version is pinned to 1.28.0 to match CI's JDK 17. Leaving `googleJavaFormat()` unpinned makes Spotless pick the newest version the *current* JVM allows, so a developer on JDK 21 and CI on JDK 17 would reformat each other's code forever. Raise the pin only together with the CI JDK.

If a build fails before any of your code is compiled, check the wrapper and JDK first — it is almost certainly one of these, not the change under review.

### Java 8 is a deliberate, standing decision — do not "modernize" it

Targeting Java 8 was reviewed and kept on purpose, to keep the library usable by Spring Boot 2.x / `javax.persistence` consumers still on a Java 8 JVM. It is not neglect, and raising it is not an improvement to offer unprompted.

The review that settled it: bumping to 11 buys only `Set.of`/`List.of`/`var` here (~10 lines, no behaviour change) while cutting off Java 8 users; 17 additionally buys `instanceof` pattern matching, which would tidy the 12-branch cast chain in `MybatisClauseBuilder.formatValueForSQL`, but a 17 target effectively means "Spring Boot 3 only" — which would make the whole `javax`/`jakarta` dual-namespace machinery pointless. Raising the target also does **not** improve runtime performance; that is decided by the consumer's JVM, not by the bytecode level. If the target is ever raised, skip 11, go straight to 17, and pair it with dropping `javax` support as a 1.0 breaking release.

The larger wins are version-independent. The 838 duplicated lines across the twin repository interfaces and the untested SQL-generation classes are both closed now; the string-interpolated SQL is still open.

### Java 8 compatibility is enforced by `--release`, not by `targetCompatibility`

`sourceCompatibility`/`targetCompatibility` alone emit `-source 8 -target 8`, which restricts *language syntax* but still links against the build JDK's class library — `String#isBlank()` and `List.of()` compile silently and produce major-52 bytecode that throws `NoSuchMethodError` on a real Java 8 JVM. The build therefore sets:

```groovy
tasks.withType(JavaCompile).configureEach { options.release.set(8) }
```

Do not remove it, and do not "fix" a `cannot find symbol` on a Java 9+ API by dropping it — that error is the guard working. Verify the output stays at `major version: 52`.

## Dependencies are `compileOnly`

Every framework dependency (spring-boot-starter, mybatis-spring-boot-starter, both `javax.*` and `jakarta.*` API jars) is `compileOnly`, so the published POM carries **zero runtime dependencies**. That is deliberate: `jakarta.persistence-api:3.2.0` and `mybatis-spring-boot-starter:3.0.5` are Java 17 bytecode (major 61), and shipping them as runtime deps forced Java-17-only jars onto Java 8 consumers — while also pushing both the `javax` and `jakarta` API jars onto everyone, which contradicts the reflective dual-namespace design. Consumers are Spring Boot apps that already have these.

Two consequences: `compileOnly` does not reach the test classpath, so anything a test needs must be repeated as `testImplementation` (the `dependencies` block already mirrors all six); and adding a new `implementation` dependency silently re-introduces the problem — check `build/publications/maven/pom-default.xml` for `<scope>runtime</scope>` after any dependency change.

## Release

Do not hand-edit `VERSION` in `build.gradle`. Pushing a tag matching `X.Y.Z` triggers `.github/workflows/tag.yml`, which rewrites `VERSION`, runs `./gradlew publishToMavenCentral` with the GPG/Maven Central secrets, and commits the bumped `build.gradle` back to `main`. Every push to any branch also runs `test.yml`, which regenerates and auto-commits the JaCoCo badge under `.github/badges/`.

That badge job pushes back to the branch it ran on, so two pushes seconds apart used to leave the older run committing onto a parent that is no longer the tip — it failed with `refs/heads/main:refs/heads/main [rejected] (non-fast-forward)` and the badge silently went unrefreshed. Three guards now cover it and all three are load-bearing: `concurrency` with `cancel-in-progress` drops the superseded run, `pull: '--rebase --autostash'` replays the badge commit onto whatever landed meanwhile (`tag.yml`'s version bump is the one that races legitimately), and `push_attempts: '3'` re-pulls between attempts to close the gap between that pull and the push. The badge push has no other retry path.

The `publishToMavenCentral()` call inside the `mavenPublishing` block is what registers the Central repository and creates that task. It was once deleted during a plugin upgrade, which silently removed the task and would have failed the next release with `Task 'publishToMavenCentral' not found`. If you touch the publishing block, confirm the task still exists:

```bash
./gradlew help --task publishToMavenCentral
```

## Architecture

### Three interfaces, and only the insert half differs

`MybatisRepository<T>` and `MybatisNoIdRepository<T>` used to be line-for-line identical (modulo import style) except that the former adds `@Options(useGeneratedKeys = true, keyProperty = "id")` to the two insert provider methods — 838 lines, 37% of the source, kept in sync by hand under a "mirror every change" rule. Everything they share now lives in `MybatisRepositoryBase<T>`, which both extend; each of the two keeps only its own insert provider pair and the two `default` wrappers (`insert`, `insertBatch`) that call them. There is nothing left to mirror.

**Do not lift the insert providers into the base.** Declaring them there without annotations and re-declaring them in the subinterfaces would make MyBatis' choice of declaration depend on JDK method-resolution rules; keeping the annotated declaration in exactly one place removes the question. The five shared providers are fine in the base because nothing re-declares them.

The refactor rests on two MyBatis facts, and `MybatisMapperRegistrationTest` pins both against a real `Configuration` rather than leaving them as assumptions: `Class#getMethods` surfaces a superinterface's annotated methods, so the five shared providers still register under the consumer's mapper name; and `MapperAnnotationBuilder.canHaveStatement` skips `default` methods, so the 37 wrappers are never parsed as statements. That test also pins that `useGeneratedKeys` reaches only the `MybatisRepository` side (`Jdbc3KeyGenerator` vs `NoKeyGenerator`) — the one difference that justifies two interfaces at all. There is no database and no sample app in this repo, so without it a wiring break would surface only in a consumer as `Invalid bound statement`.

`MybatisRepositoryDefaultsTest.defaultMethods_ShouldDelegateIdenticallyInBothInterfaces` predates the split and still runs all 37 wrappers on a recording stub of each interface, walking superinterfaces to find them. Its cross-interface comparison is now trivially satisfied for the 35 shared ones, but the two argument vectors it runs per method are still the only coverage those wrappers have, and both are load-bearing — the populated vector gives each same-typed parameter a *different* value (the two `Set`s, the two `Integer`s) so a swapped `distinctColumns`/`targetColumns` or `limit`/`offset` shows up, and the all-`null` vector is the only thing that reaches the `x == null ? Collections.emptyX() : x` normalisation, which the populated vector never executes. Dropping either vector makes the test pass on a real divergence — verified by deleting one interface's null guard and watching only the null-vector assertion fail. `sharedDefaults_ShouldBeDeclaredOnceOnTheBaseInterface` is what stops the duplication creeping back: it asserts each subinterface declares exactly `insert` and `insertBatch`.

Between them the three interfaces expose exactly 7 abstract provider methods (`buildSelectSQL`, `buildSelectOneSQL`, `buildCountSQL`, `buildInsertSQL`, `buildInsertBatchSQL`, `buildUpdateSQL`, `buildDeleteSQL`) annotated with `@SelectProvider`/`@InsertProvider`/`@UpdateProvider`/`@DeleteProvider` pointing at `MybatisCommand` — five on the base, the two insert ones on each subinterface. Everything else — 37 `default` methods such as `getDistinctItemsByMapOrderByLimitOffset` — is a thin wrapper that fills in empty collections and delegates to one of those 7. Adding a convenience API means adding a `default` overload on `MybatisRepositoryBase`, not new SQL code.

### Runtime entity resolution

Provider methods receive a `ProviderContext`; `MybatisEntityHelper.extractEntityClassFromMapper` walks the mapper's generic interfaces (recursively through parent interfaces) to find the `T` in `MybatisRepository<T>`, `MybatisNoIdRepository<T>` or `MybatisRepositoryBase<T>`. This is why a repository must extend one of those with a concrete entity type — there is no other source of entity type information. `MybatisRepositoryBase` is matched too because extending it directly is the supported way to get a repository with no insert; leaving it out would make that spelling fail on the first query instead of at compile time.

Consumers reach for that method from their own MyBatis interceptors, so `MybatisEntityHelper` has a no-arg constructor: the method never touches `stringHelper`, and making callers hand-build a `MybatisStringHelper` only to get at it exposed the SQL-escaping chokepoint for no reason.

### JPA annotations are read by name, not by type

`MybatisEntityHelper` inspects `annotationType().getName()` and matches the strings `jakarta.persistence.Column` / `javax.persistence.Column` (and the `Table` equivalents), invoking `name()` reflectively. That is deliberate: the library compiles against both `javax` and `jakarta` APIs (as `compileOnly`) and works under Spring Boot 2.x and 3.x without a compile-time choice. Keep new annotation handling reflective and dual-named.

Consequences to remember:
- **Only fields carrying `@Column` are mapped.** A field without it is invisible to select/insert/update, and passing its name in a condition map throws `MybatisRepositoryException`.
- Table name comes from `@Table(name=...)`, else camelCase→snake_case of the simple class name; column name from `@Column(name=...)`, else camelCase→snake_case of the field name.
- Fields are collected up the class hierarchy (stopping at `Object`), so mapped superclasses work.
- **`@Id` is never read.** The `...ById` methods hardcode the Java field name `"id"` (`Collections.singletonMap("id", id)`), and the interface signatures hardcode `Long`. An entity whose key is named or typed differently cannot use them.
- Results are memoized in eight static `ConcurrentHashMap`s on `MybatisCommand`: `FIELD_CACHE`, `TABLE_NAME_CACHE`, `FIELD_NAME_CACHE` (the `@Column` field-name set), `COLUMN_NAME_CACHE` (nested, `entityClass → fieldName → column`), `WRAPPED_COLUMN_CACHE` (nested, `entityClass → fieldName →` the backtick-wrapped column — so every clause that emits a column name pays `getColumnName` + `wrapIdentifier` once per field, not once per query), `ORDERED_FIELD_CACHE` (`entityClass → List<Field>` in `FIELD_NAME_CACHE` iteration order), `SELECT_COLUMNS_CACHE` (`entityClass →` the `", "`-joined backtick column list) and `MAPPER_ENTITY_CACHE` (mapper interface → entity class). They live on `MybatisCommand` but are only populated from `MybatisEntityHelper` — they are never invalidated, so entity metadata is assumed immutable for the JVM's lifetime. Values are unmodifiable, so a caller must not mutate what `getEntityFields` returns.
- **Only successful lookups are cached.** `getColumnName`, `getWrappedColumnName` and `extractEntityClassFromMapper` deliberately leave their failure paths uncached, so an unmapped field name keeps throwing `MybatisRepositoryException` on every call instead of being remembered as a miss. A side effect of `WRAPPED_COLUMN_CACHE` is that `isValidIdentifier`'s length cap and keyword blocklist now run once per `(entity, field)` rather than once per query — fine because entity metadata is immutable for the JVM's lifetime and `maxIdentifierLength` is programmatic-only, but it means changing that limit after the first query does not re-validate already-cached names.
- **Every cache read does a plain `get` first and only falls back to `computeIfAbsent` on a miss.** That is not stylistic. `ConcurrentHashMap.computeIfAbsent` did not get a lock-free hit path until JDK 9 (JDK-8161372): on Java 8 — a first-class target for this library — the key-found branch sits *inside* `synchronized (f)` on the bin head. Since the key is the same `Class<?>` for every thread serving the same entity, all query threads contend on one monitor, which is a scalability failure, not just overhead. Three of the mapping lambdas also capture `this`, so they allocated per call even on a hit; `getTableName` runs on every query of every kind. Keep `computeIfAbsent` on the miss path — switching to `putIfAbsent` would allow two threads to compute different `Set` instances and reopen the `FIELD_NAME_CACHE` ordering question above. **The two nested caches need the `get` on the *outer* map, not just the inner one**, and that is where most of the cost was: `getColumnName`/`getWrappedColumnName` already read the inner map with a plain `get`, but reached it through `computeIfAbsent(entityClass, …)` on every call, so a 20-column insert or `updateById` took 20 monitor acquisitions on that one line — about 40 of the 44 a wide write used to pay.
- **The caches are never invalidated, and converting them to weak keys was considered and declined.** They hold `Class<?>` keys strongly, so if this jar is ever loaded by a classloader that *outlives* the entity classes' loader — a shared servlet-container `lib/` with hot redeploy, or OSGi — the entity classes cannot be collected. That does not apply to the normal shapes: in a Spring Boot fat jar, or a WAR with the jar in `WEB-INF/lib`, the maps die with the application. Contents are bounded either way (one entry per entity class, inner maps bounded by field count, and unresolvable names throw *before* insertion so a hostile condition-map key cannot grow them). There is no speed argument either: `ClassValue.get` measured 1.97 ns against `ConcurrentHashMap.get`'s 2.42 ns, about 20 ns over a whole 20-column insert. And the fields are `protected static final` on a published public class, so changing their type is a source- *and* binary-incompatible break. If weak keys are ever wanted, **`ClassValue` is the only correct structure** — a `WeakHashMap<Class<?>, …>` would collect nothing, because `FIELD_CACHE`/`ORDERED_FIELD_CACHE` values are `Field`s whose `getDeclaringClass()` *is* the key and `MAPPER_ENTITY_CACHE`'s value keeps its key interface alive through its loader; a value that strongly references its own key pins the entry forever. Do it in the 1.0 breaking release or not at all.
- `getAllNonExcludedFields` calls `setAccessible(true)` once while populating `FIELD_CACHE`. `toMap` therefore reads fields without locking; do not reintroduce a `synchronized (field)` there — the `Field` objects are shared by every thread through the cache, so locking them serialises batch inserts across the whole JVM.
- **Neither insert path goes through `toMap` any more.** `buildInsertSQL` and `buildInsertBatchSQL` both read values straight off `ORDERED_FIELD_CACHE`'s `List<Field>`, which is built in `FIELD_NAME_CACHE` iteration order — the same order `INTO_COLUMNS` is emitted in, so columns and values stay aligned. That list resolves duplicate field names the way `toMap`'s `put` did (the last `Field` up the hierarchy wins), and a field whose `get` throws yields `null`, matching the old "absent key → `map.get` returns null" path. Caching the wrapped column names in a second list and pairing the two by index was tried and reverted: it measured 3-4% *slower* on a 20-column insert (the `WRAPPED_COLUMN_CACHE` hit it replaced is already cheap) while adding a second ordering invariant that, if it drifted, would write values into the wrong columns. Do not re-attempt it without a measurement that shows a win. `buildInsertSQL_ShouldAlignValuesWithColumns` pins the single-insert column-value pairing with **distinct** values, because `buildInsertSQL_ShouldKeepColumnOrderStable` builds all-`null` rows and so cannot see a misalignment at all. `MybatisSqlGenerationTest.buildInsertBatchSQL_ShouldKeepColumnOrderStable` pins the whole generated statement, because a single-slot drift between the two orders would silently write values into the wrong columns. Its `TwelveColumn` rows must carry **distinct** values whose suffixes match the column names (`c07` → `'a07'`) — the test was first written with all-`null` fields, and an all-`null` row renders identically no matter how the order is scrambled, so it caught nothing. Any test that claims to guard this alignment has to encode the column-value pairing in the pinned string.
- **`toMap` must build a plain `new HashMap<>()`, and `ORDERED_FIELD_CACHE` must stay in lockstep with it.** That map's bucket order *is* the UPDATE `SET` order, because `updateById`/`updateByMap(entity, …)` pass `MybatisCommand.toMap(entity)` straight in as the `updateMap`. INSERT no longer reads the map, but it emits the same order for free: `FIELD_NAME_CACHE` is a `HashSet` holding the same keys added in the same sequence, so its iteration order — and therefore `ORDERED_FIELD_CACHE`'s — matches the `HashMap`'s. Keep it that way; if the two drift, one entity renders its columns in one order for INSERT and another for UPDATE. Pre-sizing the map (`new HashMap<>(fields.size() / 0.75f + 1)`) picks a different table capacity than the default-16-then-double path, which silently reorders the emitted columns — confirmed for entities with 3, 4, 5, 12 and 24 `@Column` fields. The SQL stays semantically correct (`SQL.VALUES` keeps each column paired with its value), so nothing fails; only the text changes. `MybatisSqlGenerationTest.buildInsertSQL_ShouldKeepColumnOrderStable` pins the generated string for 4- and 12-column entities to catch exactly this, and `buildInsertSQL_ShouldFollowSameOrderAsToMap` compares the two orders directly across 2-, 3-, 4-, 5-, 12- and 24-column entities — the sizes that straddle the `HashMap` resize thresholds. Those two are the direct guard on the order itself; `buildUpdateSQL` is reachable from a test through `MybatisSqlGenerationTest.providerContextOf` (see Testing below), but it pins the SET *protocol* rather than the field ordering. The same hazard is why `getEntityFields` caches the very `Collectors.toSet()` result the old code produced instead of switching to a `LinkedHashSet`.
- **A whole-column SELECT emits one pre-joined string, not one `SELECT` call per column.** `getSelectColumnList` caches `", "`-joined backtick columns in `SELECT_COLUMNS_CACHE`; MyBatis' `AbstractSQL` joins the SELECT list with `", "` anyway, so the rendered statement is identical. The empty case is load-bearing: an entity with no `@Column` field yields `""`, and the caller must skip `SQL#SELECT` entirely — passing the empty string puts a blank column into the list and changes the text. `MybatisSqlGenerationTest.getSelectColumnList_ShouldRenderSameAsColumnByColumn` and `…_ShouldEmitNothingWhenEntityHasNoColumns` pin both halves. Despite the name, that cache also feeds `buildInsertBatchSQL`'s `INTO_COLUMNS` — the batch path used to re-join the same set, in the same order, with the same `", "` on every call, so the string is byte-identical; `buildInsertBatchSQL_ShouldUseSameColumnListAsSelect` ties the two together. The method keeps its `Select` name only because it is `protected` on a published class.

### Batch insert rows are separated with `ADD_ROW()`, not with parentheses of our own

MyBatis' `AbstractSQL.insertSQL` renders each entry of its `valuesList` wrapped in one pair of parentheses (`sqlClause(builder, "VALUES", list, "(", ")", ", ")`). So handing `INTO_VALUES` a single pre-joined string like `(1,'a'), (2,'b')` produces `VALUES ((1,'a'), (2,'b'))` — MySQL reads the inner parens as row values and rejects it (`Operand should contain 1 column(s)`; sqlite says `row value misused`). The library shipped that shape from its first commit, so `insertBatch` never produced runnable SQL.

`buildInsertBatchSQL` therefore appends one row per `INTO_VALUES` call with `ADD_ROW()` between rows and lets MyBatis add the parentheses; the row separator in the rendered text is `\n, `. A single reused `StringBuilder` (`row.setLength(0)` per row) keeps the per-row string count at one. Do not go back to building the whole `VALUES` body yourself, and do not add parentheses around a row.

The finished batch statement is rendered into a **pre-sized** buffer, not through `SQL#toString`. `AbstractSQL.toString` is hardcoded as `new StringBuilder()`, so a 1000-row × 20-column statement (286 KB in the benchmark) grew a capacity-16 buffer through ~14 doublings, copying roughly twice the final size and discarding every intermediate array. `buildInsertBatchSQL` now sums `row.length() + 8` as it builds each row and renders with `sql.usingAppender(new StringBuilder(estimate))`, which runs the *same* `sql(Appendable)` path `toString` uses — the text is byte-identical, and `buildInsertBatchSQL_ShouldKeepColumnOrderStable`'s pinned statement is what proves it. The estimate is only a capacity hint; being wrong costs nothing but a resize.

**The justification is allocation, not latency, and the numbers should be quoted honestly if this is ever revisited.** Measured on a 1000-row × 20-column batch: allocation per call **3268 KB → 2903 KB (−11%, ~365 KB of garbage removed)**, while wall-clock stayed inside noise (1.65–1.79 ms before, 1.53–1.76 ms after — the ranges overlap). Do not re-justify this as a speed win; it is not one.

`usingAppender` has existed since MyBatis 3.4.0 (verified with `javap`), well below the 3.5.2 floor `ADD_ROW()` already imposes on this path, so it adds no new version requirement.

A second, larger batch-path optimisation was **measured and declined**: `buildInsertBatchSQL` calls `formatValueForSQL` per value and immediately copies the returned `String` into the row buffer, so a 1000×20 batch throws away 20 000 short-lived `String`s. An append-shaped `appendValueForSQL` (specialising only the `String` and `Number` branches, delegating the rest) measured −40% on row-body construction for `String` columns and −54% for `Long`, about 0.28 ms of the 1.7 ms whole-statement build. It was declined because it puts a second value→SQL-text dispatch beside `formatValueForSQL`, and that chain is the escaping chokepoint — the rule above exists precisely because a branch that builds its own text is one edit away from building its own quotes, and this codebase has already shipped two silent-corruption bugs of exactly that shape (`O''Brien` → `O""Brien`, and the `Map` literal quoting). 0.28 ms in front of a multi-millisecond round trip does not buy that risk. If it is ever attempted, it needs an oracle test comparing the two paths over a generated corpus of every supported type, in the style of `quoteAndEscape_ShouldMatchQuotedEscapeSingleQuote`.

`ADD_ROW()` was added in MyBatis **3.5.2**, so that is the floor for `insertBatch` (verified with `javap`: absent in 3.5.1, present in 3.5.2). MyBatis is `compileOnly`, so a consumer pinned to `mybatis-spring-boot-starter` 2.0.0/2.0.1 would get a `NoSuchMethodError` — but that same consumer was previously getting SQL the database refused, so nobody can have been depending on it.

### Condition map protocol

`Map<String, Object>` keys are `fieldName` or `fieldName:conditionType`, split on the first `:` by `MybatisStringHelper`. `Condition` is a strategy enum (`eq`, `ne`, `not`, `in`, `notIn`, `null`, `notNull`, `contains`, `notContains`, `startsWith`, `endsWith`, `lt`, `lte`, `gt`, `gte`); an unknown code silently falls back to `eq`. Adding an operator = adding one enum constant with its `buildClause`, nothing else. `MybatisClauseBuilder` also unwraps a nested `whereConditions` key if the map has one.

`orderByConditions` is a `List<String>` where a `-` prefix means DESC.

### UPDATE SET protocol: an absent key is untouched, a present `null` writes SQL NULL

This is the contract for `updateMap`, and it is deliberate — not an accident of `HashMap` iteration:

- **Key absent from `updateMap` → the column does not appear in the statement at all.** `buildUpdateSQL` iterates `updateMap.entrySet()` and emits one `SET` per entry, so a column nobody mentioned is never written and keeps its stored value.
- **Key present with a `null` value → `` `column` = null `` is emitted, and the column is updated to SQL NULL.** `null` reaches `buildEqualClause` → `buildComparisonClause` → `formatValueForSQL(null)`, which returns the literal string `"null"`. There is no null-filtering step anywhere on this path, and there must never be one: "skip nulls" and "write NULL" are both plausible-looking behaviours, and silently choosing the first makes clearing a column impossible through this API.

So `{"name": "kim"}` leaves `memo` alone, while `{"name": "kim", "memo": null}` clears `memo`. `MybatisSqlGenerationTest.buildUpdateSQL_ShouldOmitAbsentKeysAndAssignNullForNullValues` pins both halves **in one statement** — a test that only checks the null case cannot tell "writes NULL" apart from "writes NULL and also writes every other column", and one that only checks the absent case cannot see a null being skipped. `buildUpdateSQL_ShouldAssignNullWhenOnlyNullValuedKeyGiven` additionally pins that an all-null `updateMap` still produces a real `SET`, so a future "drop null entries first" optimisation would surface as an empty-map exception rather than as a silently narrowed statement.

Two consequences that follow from this and are easy to get wrong:

- **Entity-based updates are a full-row overwrite, not a partial update.** `updateById(entity, id)` and `updateByMap(entity, where)` pass `MybatisCommand.toMap(entity)` straight in, and `toMap` puts **every** `@Column` field into the map regardless of value. A field left `null` on the entity is a present key with a `null` value, so it clears that column. Callers who want a partial update must use `updateMapById` / `updateMapByMap` and pass only the keys they intend to write. (The one exception is a field whose `Field#get` throws: `toMap` logs and skips it, which lands on the absent-key side and leaves the column untouched.)
- **The `fieldName:conditionType` suffix is a WHERE-only protocol.** `updateMap` keys are passed whole to `getColumnName`, so `"name:eq"` is looked up as a field literally named `name:eq` and throws `MybatisRepositoryException`. It never silently resolves to `name`.

`buildUpdateSQL` rejects a null or empty `updateMap` up front, next to the existing `whereConditions` guard. Empty used to render `UPDATE t WHERE (…)` with no `SET` at all — a statement every database refuses — and null threw a bare `NullPointerException` out of `entrySet()`. **The `whereConditions` check must stay first**, so that when both are empty the caller hears about the missing WHERE (the one that risks touching every row) rather than the missing SET; `buildUpdateSQL_ShouldCheckWhereConditionsFirst` pins that ordering. Neither guard may be widened into "drop entries whose value is null" — that would silently re-break the rule above.

### SQL is string-interpolated, not parameter-bound — this is the security boundary

`MybatisClauseBuilder.formatValueForSQL` inlines literals directly into the SQL text (there are no `#{}` placeholders anywhere). Two chokepoints in `MybatisStringHelper` are therefore load-bearing and must not be bypassed:

- `escapeSingleQuote` — escapes `'`, backslash, NUL, newline/CR/tab/backspace/formfeed, `"`, and SUB (`\u001A`) for every value that reaches the SQL string. `quoteAndEscape` is the same gate with the surrounding quotes fused in, so it sizes the buffer once instead of copying a long value through a concat chain; every branch that used to write `"'" + escapeSingleQuote(v) + "'"` now calls it. It reproduces that expression exactly, `null` included — the old concat rendered the literal `'null'` (reachable when a `ValueEnum.getValue()` returns null), so it does too. `MybatisStringHelperTest.quoteAndEscape_ShouldMatchQuotedEscapeSingleQuote` holds the two against each other over the same generated corpus that pins `escapeSingleQuote`; a new quoting path must go through one of these two, never build its own quotes.
- `wrapIdentifier` → `isValidIdentifier` — allowlist regex `^[a-zA-Z][a-zA-Z0-9_]*$`, a large SQL-keyword blocklist, and a length cap, before wrapping in backticks.

Any new value type in `formatValueForSQL`, or any new clause that emits a column name, must route through these. That rule is why `formatValueForSQL`'s temporal branches still write `"'" + … + "'"` inline instead of sharing a `quote()` helper: a named, escaping-free quoting helper is exactly the thing a later contributor reaches for with an unsafe value, and the only thing it would buy is one `StringBuilder` resize per datetime literal.

Every clause shape lives in `MybatisClauseBuilder` (`buildComparisonClause`, `buildInstrClause`, `buildEndsWithClause`, `buildNullClause`, `buildInClause`, `buildEqualClause`); `Condition` is a dispatch table that picks one and supplies the operator. That is a cohesion rule, **not** a performance one — measured against the previous inline `` "`" + col + "` = " + v `` concatenations it lands inside nanosecond-scale noise, because C2 already collapses an inline concat chain into a single sized allocation (behind a helper with a variable operator the `INSTR` branch can even cost a few ns more). The reason to keep it is that a branch which builds its own SQL text inline is one edit away from building its own quotes too, which bypasses the escaping chokepoint above. Every branch is pinned by exact-string assertions in `MybatisSqlGenerationTest.condition_ShouldBuildExpectedClauses`, so a spacing change fails loudly.

`MybatisRepositoryProperties` caps blast radius (`maxInClauseSize` 1000, `maxStringValueLength` 1 MiB, `maxIdentifierLength` 256) and also holds `zoneId`, the wall clock used for datetime literals (default UTC). It is a plain `getInstance()` singleton, **not** bound with `@ConfigurationProperties`; the size limits remain programmatic-only, while `zoneId` is the one value read from `application.yml` (`mybatis-repository.timezone`, declared in `META-INF/additional-spring-configuration-metadata.json` for IDE completion) — see the registration note below for why that happens in an `ApplicationContextInitializer` and not in a bean.

`zoneId` is `null` when unset, and that null is load-bearing: `getZoneId()` (used by `Instant`, `OffsetDateTime`, ISO-8601 strings) falls back to UTC, while `getDateZoneId()` (used by the `java.util.Date` branch) falls back to `ZoneId.systemDefault()`. Those are the two different defaults those paths shipped with before the setting existed, so a consumer who configures nothing gets byte-identical SQL, and one who configures a zone gets a single wall clock for every type. Collapsing the two getters into one would silently move stored values for somebody. The string setter is named `setTimezone`, not an overload of `setZoneId`, because a same-named overload makes `setZoneId(null)` ambiguous and gives JavaBean binding two candidates.

The zone-carrying branches of `formatValueForSQL` all funnel through `MybatisStringHelper.instantToString`, so `Instant`, `OffsetDateTime` and `ZonedDateTime` land on one wall clock; `LocalDateTime`/`LocalDate` are already wall clocks and are deliberately not shifted. Four branch-ordering facts are load-bearing:

- **`java.sql.Date` and `java.sql.Time` must be tested before `java.util.Date`.** They are subclasses, but their `toInstant()` throws `UnsupportedOperationException`, so the `Date` branch blows up on them. They are rendered through `toLocalDate()` / `toLocalTime()`, which decode the epoch millis with **`ZoneId.systemDefault()`, deliberately ignoring `mybatis-repository.timezone`** — these are JDBC's local-field types, and a value produced by the driver or by `Date.valueOf(localDate)` is already normalized to the JVM zone, so re-decoding it through a different zone moves the date by a day. The cost is that a millis-constructed `new java.sql.Date(System.currentTimeMillis())` follows the JVM zone rather than the configured one; that trade was taken on purpose and `MybatisClauseBuilderTest` pins it by forcing `TimeZone.setDefault("UTC")` against a configured `Asia/Seoul`. `java.sql.Timestamp` is a real instant and stays on the `Date` branch, where it does follow `getDateZoneId()`.
- **`ZonedDateTime`, `OffsetTime` and `LocalTime` each need their own branch.** Without them they fall through to the generic `toString()` tail and `'2025-01-02T12:34:56+09:00[Asia/Seoul]'`, `'12:34:56+09:00'`, or a seconds-eliding `'12:34'` go into the SQL text. `ZonedDateTime` follows the configured zone like `OffsetDateTime`; the two time-only types have no date to anchor a conversion, so they drop the offset and keep the wall clock, matching `java.sql.Time`.
- **`Number` and `Boolean` are tested second, right after `String`.** They used to sit eleventh, so every `Long` id walked the whole temporal chain first. Nothing below them can be a `Number` or a `Boolean` — the temporal types, `Enum`, `Collection` and `Map` all exclude them — so the move changes no output for any type that is not deliberately pathological (a class extending `Number` *and* implementing `Collection`).
- **ISO-8601 strings are parsed by `MybatisStringHelper.parseIso8601`, not `Instant.parse`.** `Instant.parse` only started accepting `+09:00` in JDK 12, so on a real Java 8 consumer the same string throws. `parseIso8601` tries `ISO_OFFSET_DATE_TIME` (Java 8, accepts `Z` and `±HH:MM`), then a builder-made formatter for the colon-less `±HHMM` form that `isISO8601String` also lets through, then `Instant.parse` last — that final step is not redundant, it is the only one that accepts a leap second (`23:59:60Z`), which the other two reject under `ResolverStyle.STRICT`. When all three fail it returns `null` rather than throwing. `isISO8601String` is a cheap pre-filter that accepts 2 or 3 hyphens (a negative offset adds one) and is allowed to be loose precisely because a failed parse falls back to plain string escaping. It gates on length *before* counting characters, because the count scans the whole value and every long `TEXT`/JSON string being stored paid for a full scan that could never end in a match (0.35 ms per value at 540 000 characters). The window is 20–64: the shortest form all three parsers can read is `2025-01-02T12:34:56Z` at 20, and nothing longer than 64 survives the character-count rules. Anything the gate drops would have failed `parseIso8601` anyway and rendered as a plain quoted string, which is what `isISO8601String_ShouldOnlyRejectLengthsNoParserAccepts` pins.

Enums implementing `io.github.bestheroz.mybatis.type.ValueEnum` are rendered with `getValue()`; other enums with `name()`.

### `Collection` and `Map` bodies are escaped exactly once, at the end

Both `formatCollectionValue` and `formatMapValue` build an **unescaped** body and hand the finished string to `quoteAndEscape` once. `appendEmbeddedValue` is the reason that works, and its rule is the load-bearing part: **it must not escape anything.** `String` and `Enum` — the only two element types that can carry user text — go into the body raw; every other type is a library-formatted literal (digits, a fixed datetime pattern) with no user text in it, so it reuses `formatValueForSQL` and only swaps its `'` for `"`.

The previous shape escaped each element and *then* swapped quotes (`formatValueForSQL(e).replace('\'', '"')`), so the `''` pair that escaping had just produced became `""`: `O'Brien` was stored as `O""Brien`. Silent, unrecoverable corruption, and `ValueEnum` values went the same way. Do not reintroduce per-element escaping, and do not let a new element type reach the body without deciding which of the two halves it belongs to.

`formatMapValue` additionally used a bare `"` as **both** the JSON structural quote and the SQL literal delimiter, so the first inner quote closed the literal and MySQL read the next key as an identifier — every non-empty `Map` produced a syntax error. Like the `insertBatch` `ADD_ROW` bug, that shape shipped from the first commit, so no consumer can have been relying on it. The output is now a normal single-quoted literal.

One consequence worth knowing: because the body now goes through the chokepoint, the `"` characters inside it come out as `\"`. The text differs from the old output; the value the database stores does not (`\"` decodes to `"` inside a single-quoted literal). Hand-rolling the quotes to avoid that escape is exactly what the rule above forbids. `formatValueForSQL_ShouldKeepPlainCollectionShape` pins the plain case and `…_ShouldNotCorruptApostropheInsideCollectionOrMap` pins the fixed one.

`ensureValueLength` applies to the **whole** rendered body, not to each element. `Map` skipped the check entirely and `Collection` bounded only individual elements, so N elements just under the cap built an arbitrarily large literal — the exact runaway shape the setting exists to stop.

### Arrays and non-finite numbers are rejected rather than stringified

`byte[]` renders as a MySQL `X'..'` hex literal. Every other array type throws `MybatisRepositoryException`, and so do `Double`/`Float` `NaN`/`Infinity`.

Both used to fall through silently. An array reached the catch-all `toString()` tail, so a `byte[]` BLOB column was written as `'[B@78e03bb5'` — its Java identity hash — and the INSERT *succeeded*, leaving a garbage row nobody noticed. `NaN` rendered as the bare word `NaN`, which the database reads as a column name (`Unknown column 'NaN' in 'where clause'`). Neither has a correct silent rendering, so both fail loudly. The array check sits just before the `toString()` tail so the hot types never pay for it, and the non-finite check is inside the existing `Number` branch, guarded by `instanceof Double || instanceof Float` so integral ids skip it.

### Table names are never identifier-wrapped; column names always are

All six build methods emit the table name raw. `buildInsertBatchSQL` used to be the exception — it ran the table name through `wrapIdentifier`, which applies the *column* rules: the SQL-keyword blocklist and an allowlist regex with no `.`. So `@Table(name = "shop.orders")` and `@Table(name = "order")` threw `IllegalArgumentException` on batch insert while every other statement built fine. Do not reintroduce that asymmetry by wrapping one call site; a real fix needs a table-specific rule applied to all six at once.

Column names are the opposite and are still uneven: SELECT, ORDER BY and INSERT go through `getWrappedColumnName` → `wrapIdentifier` → `isValidIdentifier`, while WHERE and UPDATE SET build the backticks inline in `Condition` and `buildEqualClause`, skipping validation. That is not an injection hole today — a condition-map key must resolve to a real `@Column` field or `getColumnName` throws — but it means the same `@Column(name = "left")` is rejected in a SELECT and accepted in a WHERE, and the defense rests on the field-existence check rather than on the allowlist.

### `maxStringValueLength` is a runaway guard, not a column-width check

It applies to every value that becomes a quoted literal, `String` included. It did not always: the check lived only in the final "everything else → `toString()`" branch of `formatValueForSQL`, so a 5000-character `String` sailed through while the same 5000 characters in a `StringBuilder` threw. Both now go through `ensureValueLength`.

The default is 1 MiB rather than the old 4000 precisely because the old number was never enforced on the common type — turning it on at 4000 would have started rejecting long `TEXT` values that worked in every previous release. Do not lower it back to a column-width-sized number; a consumer who wants that can set it.

### Dialect assumption

Backtick identifier quoting, `INSTR` / `RIGHT` / `CHAR_LENGTH` for string conditions, and `LIMIT`/`OFFSET` make the generated SQL MySQL/MariaDB-flavoured. Anything portable across dialects would need a new abstraction, not a tweak.

### Debug logging must stay behind `isDebugEnabled`

Every build method renders its SQL exactly once and passes it through `MybatisCommand.renderAndLog`. The obvious-looking `log.debug("insert SQL: {}", sql.toString().replaceAll("\n", " "))` is a trap: SLF4J defers *formatting*, not argument evaluation, so that line rendered the statement and built a regex-replaced copy of it on every query even with debug off. On a 1000-row batch insert that is a wasted 62 KB copy and a `Pattern` compile per statement — measured at ~110 µs, about an eighth of the whole call. Keep the `isDebugEnabled` guard, keep the single render, and use `replace('\n', ' ')` (char) rather than `replaceAll` (regex).

### What the provider methods actually receive is a `ParamMap`, and `-parameters` is required

MyBatis does not hand a provider the arguments the caller passed. `ProviderSqlSource` has two modes, and this library hits both:

- **One bind parameter** (`buildSelectOneSQL`, `buildCountSQL`, `buildDeleteSQL` — `ProviderContext` does not count), where the declared type is assignable from the actual parameter object: MyBatis passes the **whole `ParamMap`** as that one argument. So `getItemByMap(myMap)` reaches the provider as `{context=null, whereConditions=myMap, param1=null, param2=myMap}`.
- **Two or more bind parameters** (`buildUpdateSQL`, `buildSelectSQL`): MyBatis binds each argument **by the provider method's parameter name**, so those get the real values.

Two consequences, both of which shipped as live bugs and are now pinned by `MybatisProviderBindingTest`:

**`-parameters` is a correctness requirement of the published jar, not a convenience.** The `whereConditions` key that `MybatisClauseBuilder.extractWhereConditions` reads out of that `ParamMap` comes from *this jar's* `MethodParameters` attribute — `ParamNameResolver` builds the map from `MybatisRepositoryBase`'s own parameter names. Without the attribute the keys are `arg0`/`arg1`, and `MapperMethod.ParamMap#get` throws `BindingException` for an unknown key instead of returning `null`, so `getItemById`, `getItemByMap`, `countAll`, `countByMap`, `deleteById` and `deleteByMap` all die in the consumer with `Parameter 'whereConditions' not found`. Until recently nothing in `build.gradle` asked for the flag: it arrived only because the `org.springframework.boot` plugin adds `-parameters` to every `JavaCompile`. That plugin is the one this file elsewhere calls a mistake to work around, so removing it — the obvious cleanup — would have silently broken six public methods. `options.compilerArgs << '-parameters'` is now set explicitly next to `options.release.set(8)`; keep both. `MybatisProviderBindingTest.compiledClasses_ShouldCarryParameterNames` fails the moment the attribute disappears (verified: `isNamePresent()` returns `false` and the name reads `arg1` when the same sources are compiled without the flag).

**A front-door `whereConditions.isEmpty()` check on a one-bind-parameter provider is dead code.** The `ParamMap` is never null and never empty, so the guard at the top of `buildSelectOneSQL` never fired under MyBatis — `getItemByMap(Collections.emptyMap())` rendered `SELECT … FROM t` with no WHERE at all, into an `Optional<T>`: a full table read, then `TooManyResultsException` on the second row. `buildUpdateSQL`/`buildDeleteSQL` survived the same hole only because `ensureWhereClause(count)` catches it afterwards; `buildSelectOneSQL` has no second net. It now unwraps first — `clauseBuilder.extractWhereConditions(whereConditions).isEmpty()` — which is why `extractWhereConditions` is `protected` rather than `private`. Do not "simplify" it back to reading the raw argument.

`extractWhereConditions` also has to survive the `ParamMap` shape itself: it uses `containsKey` before `get` (because `ParamMap#get` throws), and treats a present-but-`null` `whereConditions` as no conditions. That last branch is what turns `getItemByMap(null)` from `entity 에 포함되지 않는 필드 발견 : context` — the old behaviour, which came from iterating the `ParamMap`'s own keys as if they were field names — into the intended "where is required" error. A present-but-non-`Map`, non-`null` value still falls through to the old "treat the map itself as the conditions" path, so a consumer entity that genuinely has a `whereConditions` field keeps working.

`getItemByMap`, `countByMap` and `deleteByMap` were also the only three of the 37 wrappers that forwarded their argument without the `whereConditions == null ? Collections.emptyMap() : whereConditions` normalisation their 34 siblings apply; they do it now. That is belt-and-braces on top of the `extractWhereConditions` fix rather than the fix itself — the clause-builder change is what makes a direct provider call safe too — but leaving three of thirty-seven inconsistent is exactly the asymmetry `MybatisRepositoryDefaultsTest` exists to catch, and it could not see this one because its stubs record the raw argument and never build a `ParamMap`.

Note that `countAll()` and `getItems()` legitimately produce unfiltered statements; `MybatisProviderBindingTest.countAll_ShouldStayUnfiltered` pins that boundary so a future widening of the guard cannot take them out.

### `LIMIT`/`OFFSET` values are validated, not forwarded

`buildSelectSQL` rejects a negative `limit`, a negative `offset`, and an `offset` given without a `limit`. All three used to be forwarded straight to the builder and produced statements MySQL/MariaDB refuse — `getItemsLimitOffset(null, 20)` rendered `… FROM t OFFSET 20` (OFFSET is only valid as part of `LIMIT n OFFSET m`) and `getItemsLimitOffset(-5, -1)` rendered `… LIMIT -5 OFFSET -1`. Twelve `…LimitOffset` wrappers take these as separately-nullable `Integer`s, so passing one without the other is easy to write, and the failure only shows up at the database. Same shape as the `ADD_ROW` batch bug and the `Map` literal quoting bug: silently unrunnable SQL, so nobody can have been depending on it.

**Zero is not rejected** — `LIMIT 0` and `OFFSET 0` are both legal, and `buildSelectSQL_ShouldRejectPagingValuesMysqlRefuses` pins that boundary along with the three rejections. If offset-only support is ever wanted, MySQL's idiom is `LIMIT 18446744073709551615 OFFSET n`; rejecting was chosen to match the fail-loudly convention used for arrays and non-finite numbers.

### Input validation throws `MybatisRepositoryException`, including from `wrapIdentifier`

`wrapIdentifier` used to throw a bare `IllegalArgumentException`, and it is reachable from ordinary use rather than only from abuse: an entity with `@Column(name = "left")` makes plain `getItems()` fail, because `left` is in the keyword blocklist. Every other validation failure in the library — `appendOrderBy`'s null element, `getColumnName`'s null field name, the array/non-finite/length guards, all six build-method guards — throws `MybatisRepositoryException`, so a consumer could not catch the family in one place. It now does too. `MybatisRepositoryProperties.setTimezone` had the same wobble *inside one method* (bare `IllegalArgumentException` for an empty string, `MybatisRepositoryException` for an unparseable zone) and now uses the library exception for both. The plain numeric setters on that class still throw `IllegalArgumentException`; they are ordinary bean setters, not part of a query path.

### Safety rails on writes

`buildUpdateSQL` and `buildDeleteSQL` reject a null/empty `whereConditions` up front, then call `ensureWhereClause` with the number of conditions `buildWhereClause` actually appended. Both guards exist on purpose; keep them, and keep the second one counting rather than reading the rendered text.

`ensureWhereClause` used to scan the finished statement for the substring `where `, which the SET clause could satisfy: `UPDATE t SET \`memo\` = 'delivered somewhere else'` passed the guard with no WHERE clause at all and updated every row. The front-door check does not catch that case either — `extractWhereConditions` unwraps a nested `whereConditions` key, so `{"whereConditions": {}}` is a size-1 map that survives `isEmpty()` and then contributes zero conditions. Counting is exact: MyBatis renders `WHERE` only when the list is non-empty, so `count > 0` is precisely "a WHERE clause was emitted".

### Spring Boot registration

`MybatisAutoConfiguration` is registered twice — `META-INF/spring.factories` (Boot 2.x) and `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (Boot 3.x) — and contains two nested `@ConditionalOnClass` configurations, one per `PostConstruct` namespace. It defines no beans; the two nested configurations only log a readiness message, which now carries the resolved zone so the value is visible at boot. If you add real configuration, update both registration files.

`mybatis-repository.timezone` is applied by `MybatisTimezoneInitializer`, an `ApplicationContextInitializer` registered in `spring.factories`. Two things about that choice are load-bearing.

**Do not move it into a bean constructor.** Auto-configuration is registered through a `DeferredImportSelector`, so its beans are created after every user bean; a consumer that queries from a constructor, `@PostConstruct`, or `InitializingBean` would write those rows with the default zone while the rest of the app writes the configured one — silently, with no error. An initializer runs before refresh, which closes that window.

**Do not switch it to `EnvironmentPostProcessor`,** which is the more obvious hook. Boot 4 moved that interface from `org.springframework.boot.env` to `org.springframework.boot`, so whichever package you compile and register against, the other major silently ignores the registration — verified against 4.2.0-M1, whose jar has no `boot.env.EnvironmentPostProcessor` at all. `ApplicationContextInitializer` is a Spring Framework interface and keeps its name across Boot 2, 3 and 4. It returns `LOWEST_PRECEDENCE` so any initializer that contributes property sources has already run.

The initializer only covers contexts built by `SpringApplication`, because that is what loads `spring.factories` initializers — so `MybatisAutoConfiguration` also implements `EnvironmentAware` and applies the same value. That is not redundancy to trim: it restores a hand-built `AnnotationConfigApplicationContext` (classic non-Boot Spring, or a WAR that bypasses `SpringBootServletInitializer`), where the initializer never runs. Applying twice is safe precisely because unset is `null` — both paths compute the same value. Two consequences worth knowing: `ApplicationContextRunner` loads neither path's registration and needs `withInitializer(...)` explicitly (`@SpringBootTest` is fine, it builds a real `SpringApplication`), and `spring.autoconfigure.exclude` no longer switches the timezone off, since the initializer is not part of the auto-configuration.

Note that `zoneId` lands in a process-wide singleton, so two Spring contexts in one JVM (tests, multi-tenant setups) share the last value written.

## Testing

Tests live in `src/test/java/io/github/bestheroz/mybatis/` and must stay in the `io.github.bestheroz.mybatis` package: most helper methods are `protected`, so a test in another package cannot reach them. JUnit 5 + AssertJ, `@DisplayName` in Korean, given/when/then comment structure.

`MybatisStringHelperTest`, `MybatisClauseBuilderTest` (datetime literal zone handling only — every temporal branch plus the ISO-8601 string forms), `MybatisEntityHelperTest`, `MybatisSqlGenerationTest`, `MybatisRepositoryDefaultsTest` (the 37 `default` wrappers reached through both subinterfaces — see above), `MybatisMapperRegistrationTest` (registers real mappers with a MyBatis `Configuration` to prove the provider annotations are still discovered across the interface split), `MybatisProviderBindingTest` (drives the providers *through* MyBatis' own parameter binding rather than calling them directly — see the `ParamMap` section above; every other test calls `MybatisCommand` directly, which is why two live bugs sat on that path), `MybatisTimezoneInitializerTest`, and `MybatisTimezoneBootstrapTest` (boots a real `SpringApplicationBuilder` context to prove the zone is applied before user beans initialize) exist today.

The repository interfaces used to be the largest blind spot in the suite: 292 lines of `default` methods at 0% line coverage, because nothing ever called them. They build no SQL, but they do fill in empty collections and normalise `null`, so an argument swap or a missing null guard was invisible. Covering them took overall line coverage from ~60% to ~86%.

`MybatisSqlGenerationTest` covers the SQL-generation path by asserting on the generated string — insert, batch insert (whole statement pinned, plus the null-element guard), IN clauses, every `Condition` branch, `appendSelectColumns` and `appendOrderBy`, `ensureWhereClause`, and column-name resolution including the cached and error paths. It also pins the UPDATE `SET` protocol (absent key vs. present `null`, the empty/null `updateMap` guards, and their ordering against the `whereConditions` guard).

`ProviderContext` has a package-private constructor, so the four context-taking build methods (`buildSelectSQL`/`buildUpdateSQL`/`buildDeleteSQL`/`buildCountSQL`) cannot be reached with `new`. `MybatisSqlGenerationTest.providerContextOf` builds one reflectively instead — MyBatis is on the classpath (the unnamed module), so `setAccessible(true)` on that constructor is not blocked, and the whole rendered statement can be asserted. Use it rather than reproducing a statement clause-by-clause through `MybatisClauseBuilder`; the clause-level equivalent cannot catch a guard that runs in the wrong order or a `SET` list that never gets emitted. The older tests that assemble `SQL` by hand (e.g. `ensureWhereClause_ShouldNotBeFooledBySetLiteral`) predate that helper and are kept because they target the clause builder specifically. `MybatisStringHelperTest` pins `escapeSingleQuote` against the pre-refactor chained-`replace` implementation over a generated corpus — that oracle is the guard on the escaping chokepoint, so keep it if the implementation changes again. Tests that touch `MybatisRepositoryProperties.getInstance()` must reset it in `@AfterEach`; it is a process-wide singleton and leaks across test classes otherwise.

## Code Style

Spotless 8.10.2 runs `importOrder()`, `cleanthat()`, `googleJavaFormat('1.28.0')` and `formatAnnotations()`. CleanThat is pinned to `sourceCompatibility('1.8')` so it never rewrites code into Java 9+ constructs. Java 8 language level and API only (no `var`, no `List.of`, no `Map.of` in library code) — `options.release = 8` enforces this at compile time. Existing comments and log messages are Korean; match the surrounding file.
